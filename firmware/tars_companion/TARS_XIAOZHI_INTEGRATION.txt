TARS 0.17.0-xiaozhi + Companion

架构
机器人麦克风 -> ESP32 I2S -> 16kHz 单声道、60ms Opus -> 本地 WSS 8766
-> Companion 解码，进行本地 TARS/Hello TARS 唤醒和静音检测
-> 豆包端到端实时语音（PCM 16k 输入，模型 1.2.6.1，音色 S_vXjewQyk2）
-> PCM 24k 回复 -> Companion 转成 PCM 16k，再编码 Opus
-> ESP32 缓存完整播放段、解码 -> I2S -> 功放 -> 喇叭。

采用小智的 WebSocket v1/Opus 音频组织方式，并加入协商确认的 TARS 缓存播放扩展。
这是对现有 TARS 固件的适配，不是整套原版小智固件，也不要求 DeepSeek。
不对每个音频包做应用层 ACK；TCP/TLS 提供传输完整性。
有界队列溢出时中止当前话语，不把旧音频或旧命令重放到新会话。

运动
独立的配对控制连接保留在 8765，运动安全租约仍为 2 秒。
语音连接和运动租约分别处理失败；控制重连不再直接终止麦克风。
只接受当前话语中的明确动作，校验固定动作名称、否定词和支持条件。
必须等 ESP32 实际播放完成的确认，才检查状态、Arm、执行、Disarm。
不重试不确定的动作；一轮动作绑定同一个控制会话。
0.16.3-motionpack 的运动组件文件保持一致，包括固化在运动代码中的舵机零位和方向。
Wi-Fi 与配对配置保留在原 NVS；射频校准等系统记录可能在启动时更新。

唤醒与记忆
唤醒识别在电脑本地完成，待机音频不上传豆包。
唤醒后连续对话窗口为 180 秒；无须在电脑点按钮。
播放和运动期间不支持语音打断。
persona 在 tars-seeduplex.json；每轮沿用相同的人格与语言规则。
data/tars-voice.sqlite3 保存长期记忆，每轮注入近期上下文，并提供 memory_lookup 检索历史。
电脑须保持开机、登录且 Companion 运行；机器人不独立保存云端对话记忆。

启动
新服务入口：Start-Tars-Xiaozhi.ps1 -Unattended
使用现有 tars-service.local.json、wifi-audio.local.json 和 Windows 加密 API Key 文件。
免费额度沿用 data/free-allowance.sqlite3 的扣减记录，不重置余额。
data/stop.request 可请求结束服务；无需再次粘贴 API Key。
不要公开配对文件、API 凭据、TLS 私钥、记忆数据库或整机 Flash 备份。
TLS 公共信任证书编入固件；私钥仅保留在当前电脑 data/tls。

本次实机发现并修复
1. 一般堆与 TLS 过度占用片内内存：一般分配与 TLS 改用 PSRAM。
2. I2S DMA 懒分配失败：开机先预留 RX/TX DMA，保持通道禁用、功放静音。
3. 60ms Opus 的真实调用栈超过原 16KiB：改为 48KiB PSRAM 栈，实测剩余值可查询。
4. Wi-Fi 关联不等于 DHCP 完成：拿到 IPv4 后才连接。
5. 重连不等待持续采集任务瞬间空闲，使用会话代次清理旧数据。

网络事实
实测 ESP32 地址 192.168.0.103、网关 192.168.0.1；电脑地址 192.168.1.2。
电脑观察到对端 192.168.1.3，连接经过中间设备，不能把它的 MAC 当作 ESP32 的 MAC。
这不单独证明之前断线由硬件或路由器引起。

诊断
audio.transport 为只读查询：目标 URI、实际 IP、错误、代次、栈余量、片内空闲内存。
error/fault_line 为最近历史故障，成功连接后可能仍保留；需结合新代次、连接和实时数据判断。
evidence/xiaozhi-regression.json：电脑端回归与真实 Opus 唤醒样本测试。
evidence/xiaozhi-hardware.json：实机采集、播放、重连结果。
evidence/xiaozhi-cloud-smoke.json：自动录音样本输入、真实云回复与机器人播放结果。
只有标记 passed=true 的实际报告代表对应检查通过，编译成功不代表实机功能通过。
